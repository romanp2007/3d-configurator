# Руководство по технологиям проекта

Этот документ объясняет, какие технологии используются в 3D-конфигураторе, как они устроены и какие задачи решают именно в контексте этого проекта — браузерного редактора 3D-сцен с drag-and-drop, гизмо-управлением и сохранением сцен на сервер.

---

## Архитектура верхнего уровня

Проект — монорепозиторий из трёх workspace'ов на npm:

- **`client/`** — фронтенд (React + Vite), всё, что видит пользователь.
- **`server/`** — REST API на Express, отвечает за хранение сцен и файлов.
- **`shared/`** — общие TypeScript-типы (например, `SceneData`), чтобы FE и BE говорили на одном языке.

Базовый принцип: фронт и бэк — два независимых деплоя, общаются по HTTP, типы переиспользуют через `shared/`.

---

## Frontend

### React 18

**Что это.** Библиотека для построения UI на основе компонентов и однонаправленного потока данных.

**Зачем в проекте.** Редактор — это десятки реактивных панелей: инспектор свойств, каталог объектов, тулбар, список сцен. React даёт декларативный способ держать DOM синхронным с состоянием стора без ручных `document.querySelector`.

**Какую проблему решает.** Без React пришлось бы вручную перерисовывать инспектор каждый раз при изменении трансформа объекта. С React достаточно обновить Zustand-стор — компоненты, подписанные на нужные поля, перерисуются сами.

### TypeScript 5

**Что это.** Надстройка над JavaScript со статической типизацией.

**Зачем в проекте.** Сцена — сложная структура: массив объектов разных типов (`box | sphere | model | …`), у каждого свои поля. TS не даёт случайно прочитать у `plane` поле `radius`, которого там нет.

**Какую проблему решает.** Контракт между клиентом и сервером (`SceneData` в `shared/types/`) проверяется компилятором на обоих концах. Если бэк изменил формат — фронт сразу краснеет в IDE, а не падает в проде.

### Vite 5

**Что это.** Сборщик и dev-сервер на основе нативных ES-модулей и esbuild.

**Зачем в проекте.** Быстрый HMR (hot module replacement) — критично, когда правишь шейдеры и материалы и хочешь видеть результат мгновенно. Прокси `/api → http://localhost:3000` встроен в `vite.config.ts`, что упрощает разработку фронта против локального бэка без CORS-плясок.

**Какую проблему решает.** Webpack пересобирал бы проект с тяжёлым Three.js по несколько секунд при каждой правке. Vite обновляет модуль за миллисекунды.

### Three.js + @react-three/fiber + @react-three/drei

**Three.js** — низкоуровневая библиотека для WebGL: сцены, камеры, меши, материалы, лучи.

**@react-three/fiber (R3F)** — реконсилятор React для Three.js. Позволяет описывать 3D-сцену в JSX:
```tsx
<mesh position={[0, 1, 0]} onClick={handleClick}>
  <boxGeometry args={[1, 1, 1]} />
  <meshStandardMaterial color="orange" />
</mesh>
```

**@react-three/drei** — коллекция готовых хелперов поверх R3F: `OrbitControls` (вращение камеры мышью), `TransformControls` (гизмо для перемещения/вращения/масштабирования), `useGLTF` (загрузка `.gltf/.glb` моделей), `Grid`, `Environment`.

**Зачем в проекте.** Это ядро редактора. R3F переводит императивный API Three.js в декларативный React-стиль, что критично для синхронизации сцены со стором: добавил объект в `useSceneStore` — R3F сам создаст mesh; удалил — он сам уберёт его из сцены и освободит GPU-ресурсы.

**Какую проблему решает.** На голом Three.js пришлось бы вручную писать `scene.add(mesh)`, `scene.remove(mesh)`, `geometry.dispose()`, отслеживать события мыши через raycaster. R3F делает всё это автоматически через жизненный цикл React-компонентов. Drei экономит сотни строк на стандартных контролах гизмо и камеры.

**Важный нюанс.** R3F-компоненты (`<mesh>`, `<group>`) не являются DOM-элементами и должны жить только внутри `<Canvas>`. UI (тулбар, панели) — обычный React DOM снаружи `<Canvas>`. Эти два дерева не смешиваются.

### Zustand + zundo

**Zustand** — минималистичный state-менеджер: один стор = один хук, никаких провайдеров и редьюсеров.

**zundo** — middleware, оборачивающий стор и автоматически складывающий каждое изменение в стек истории.

**Зачем в проекте.** Три стора с чёткими ролями:
- `useSceneStore` — массив объектов сцены и выделение (с `zundo` → бесплатный undo/redo).
- `useEditorStore` — UI-состояние: режим гизмо, видимость панелей, флаги сетки/снапа.
- `useHistoryStore` — управление стеком undo/redo.

**Какую проблему решает.** Двусторонняя синхронизация «гизмо ↔ инспектор»: пользователь тащит объект гизмо — обновляется стор — поле `position.x` в панели свойств меняется автоматически. И наоборот: вводит число в инпут — стор обновляется — mesh в сцене сдвигается. Без центрального стора пришлось бы прокидывать колбэки между несвязанными деревьями (Canvas и DOM).

С `zundo` undo/redo получается «из коробки»: не нужно вручную делать снапшоты на каждое действие.

### react-dnd + react-dnd-html5-backend

**Что это.** Библиотека drag-and-drop с разделением на «источники» (drag sources) и «цели» (drop targets).

**Зачем в проекте.** Каталог объектов слева — источник перетаскивания; `<Canvas>` — цель. Пользователь тащит «Куб» → отпускает над сценой → создаётся объект.

**Какую проблему решает.** HTML5 DnD API сырой и плохо работает с canvas. react-dnd абстрагирует его и даёт общий API. Точку отпускания (DOM-координаты) нужно ещё перевести в 3D-координаты — это делается raycaster'ом по полу-плоскости.

### TailwindCSS

**Что это.** Utility-first CSS-фреймворк: классы вроде `flex items-center gap-2 bg-slate-800`.

**Зачем в проекте.** UI редактора — много мелких панелей с одинаковыми отступами/границами/тенями. Tailwind избавляет от написания CSS-файлов и `BEM`-имён, всё стилизуется прямо в JSX.

**Какую проблему решает.** Согласованность дизайна (один `bg-slate-800` везде = одинаковый тёмный фон) и отсутствие проблем с каскадом и специфичностью.

### nanoid

Генерация коротких уникальных ID для объектов сцены. Лёгкая (≈130 байт), URL-безопасная, без зависимостей. Используется при создании каждого `SceneObject`.

## Backend

### Node.js 20 + Express

**Express** — минималистичный HTTP-фреймворк. Маршруты `/api/scenes` (CRUD сцен) и `/api/assets` (загрузка/выдача файлов моделей).

**Зачем в проекте.** Проект небольшой — одна сущность `Scene` и файловое хранилище. Express с парой роутеров и middleware закрывает 100% потребностей без оверкиллов вроде Nest.

### Prisma + PostgreSQL 16

**Prisma** — ORM с генерацией типизированного клиента из `schema.prisma`.

**PostgreSQL** — реляционная БД с поддержкой типа `Json` (JSONB).

**Зачем в проекте.** Сцена хранится как **один JSON-документ** в поле `Json`, а не нормализуется по таблицам «объекты», «материалы», «трансформы». Это сознательный выбор: сцена всегда читается и пишется целиком, нормализация только усложнила бы код без выгод по производительности.

**Какую проблему решает Prisma.** Типобезопасность запросов: `prisma.scene.findUnique({ where: { id } })` возвращает типизированный объект, а не `any`. Миграции через `prisma migrate dev` версионируются вместе с кодом.

### Zod

**Что это.** Библиотека рантайм-валидации с выводом TypeScript-типов из схем.

**Зачем в проекте.** Каждый POST/PUT приходит из браузера — доверять нельзя. Zod-схема для `SceneData` проверяет тело запроса перед записью в БД и одновременно даёт статический тип для хендлера.

**Какую проблему решает.** TS-типы стираются на рантайме — без Zod кривой JSON просто записался бы в БД и сломал клиент при следующей загрузке. Zod ловит это на границе API.

### Multer

Middleware для приёма `multipart/form-data` — загрузка `.glb`/`.gltf`-моделей в `/api/assets`. Альтернатив на Express практически нет.

### CORS + dotenv

`cors` разрешает запросы с фронтового домена в проде (в деве хватает Vite-прокси). `dotenv` подгружает `.env` (DATABASE_URL, порт, секреты).

## Shared

Workspace `shared/` экспортирует только типы (`SceneData`, `SceneObjectData`, перечисление типов объектов). Импортируется и клиентом, и сервером — благодаря npm workspaces без публикации в реестр.

**Какую проблему решает.** Запрещает дублирование. Если на бэке добавили поле `environment.fog`, фронт сразу видит его в типах. Без `shared/` пришлось бы поддерживать две копии типов и ловить рассинхрон в рантайме.

## Инфраструктура и тулинг

### Docker + docker-compose

`docker-compose.yml` поднимает PostgreSQL одной командой — разработчику не нужно ставить Postgres локально. `docker-compose.prod.yml` собирает образ всего приложения для деплоя.

### ESLint + Prettier

ESLint — статический анализ (неиспользуемые переменные, ошибки React-хуков). Prettier — форматирование. `eslint-config-prettier` отключает правила ESLint, конфликтующие с Prettier.

### Vitest

Тест-раннер на базе Vite. Использует ту же конфигурацию сборки, что и сам проект — не нужно настраивать отдельный jest+ts-jest+babel.

### concurrently

Запуск `npm run dev:client` и `npm run dev:server` одной командой `npm run dev` с цветными префиксами в логах.

### tsx

Замена `ts-node-dev`. Запускает TS-файлы напрямую через esbuild и перезапускает сервер при изменениях. Быстрее и не требует отдельного `tsconfig` для рантайма.

## Как технологии связаны между собой

```
   ┌───────────────────────────────────────────────┐
   │  Браузер                                      │
   │                                               │
   │  ┌─────────────────────┐  ┌────────────────┐  │
   │  │ Canvas (R3F + drei) │  │ UI (Tailwind)  │  │
   │  │   meshes, gizmo     │  │ панели, каталог│  │
   │  └─────────┬───────────┘  └────────┬───────┘  │
   │            │                       │          │
   │            └───────┬───────────────┘          │
   │                    ▼                          │
   │         ┌──────────────────────┐              │
   │         │ Zustand (+ zundo)    │              │
   │         │ scene / editor stores│              │
   │         └──────────┬───────────┘              │
   │                    │ fetch /api/scenes        │
   └────────────────────┼──────────────────────────┘
                        │
                  Vite proxy / CORS
                        │
   ┌────────────────────┼──────────────────────────┐
   │  Node.js           ▼                          │
   │         ┌──────────────────────┐              │
   │         │ Express + Zod        │              │
   │         └──────────┬───────────┘              │
   │                    ▼                          │
   │         ┌──────────────────────┐              │
   │         │ Prisma → PostgreSQL  │              │
   │         │       (Json field)   │              │
   │         └──────────────────────┘              │
   └───────────────────────────────────────────────┘

   shared/types — общий контракт SceneData для обоих концов
```

**Поток данных при перетаскивании куба:**
1. `react-dnd` фиксирует drop над `<Canvas>`.
2. Координаты экрана → 3D через raycaster (Three.js).
3. `useSceneStore.addObject()` добавляет запись с `nanoid()`-id.
4. `zundo` сохраняет снапшот в стек истории.
5. R3F видит новый элемент массива → рендерит `<mesh>`.
6. Инспектор (DOM) подписан на `selectedId` → показывает свойства.
7. По кнопке «Save» фронт шлёт `SceneData` на `/api/scenes`.
8. Express → Zod валидирует → Prisma пишет JSON в Postgres.

Каждая технология закрывает ровно один слой; границы между ними — это и есть архитектура проекта.
